# Runtime realtime V2 con evidencia de dos velocidades y estado durable

V2 separa el régimen estructural del timing táctico, hace alcanzable la salida táctica y activa el trailing sólo después del umbral configurado. También añade checkpoint atómico, recuperación desde journal, IDs de orden deterministas y observabilidad del estado protector. No está listo para deploy por tres blockers **[confirmed]**: freshness acepta eventos antiguos como actuales, el allowlist del endpoint DEMO permite exfiltrar credenciales y los fills parciales no se integran como exposición ejecutada. La ausencia de metadatos Git en `cryptoagent3.0` impidió distinguir estas líneas de código preexistente; el análisis cubre el estado actual de los seis archivos solicitados.

Watch for: **[confirmed]** bypass del allowlist REST y envío de credenciales a un host atacante; **[confirmed]** freshness basada sólo en hora de recepción; **[confirmed]** ventana de crash entre fill y checkpoint/journal; **[confirmed]** fills parciales tratados como órdenes no llenadas; **[confirmed]** checkpoint inválido sin fallback; **[confirmed]** dashboard que presenta intentos incompletos como ejecución exitosa; **[confirmed]** ausencia de pruebas del runtime V2.

**Verdict**: NEEDS_CHANGES

## High-level view

La separación structural/tactical está materializada en scores y coberturas independientes. El estructural habilita entradas y el táctico decide timing de entrada y salida; una prueba aislada produjo `EXIT_LONG` con reversión táctica y persistencia cero, por lo que SELL ya no es inalcanzable.

El stop inicial se mantiene hasta que el máximo desde entrada llega a `entry * 1.015`; en ese punto el probe cambió el stop de `97.00` a `98.9625`. **[confirmed]** Entry, máximo, cooldown y candidatos se guardan con reemplazo atómico y `fsync`, pero el checkpoint no forma una unidad recuperable con la orden y el journal, y un checkpoint ilegible bloquea la recuperación alternativa.

**[confirmed]** La validación posterior a una orden sólo acepta `FILLED`. Un resultado `PARTIALLY_FILLED` ya cambió el balance real, pero se convierte en `HOLD/ORDER_NOT_FILLED`; la reconciliación posterior no conserva necesariamente el precio real del fill ni reconoce exposiciones por debajo del umbral de dust.

**[confirmed]** Freshness mide cuánto tiempo lleva el último mensaje en el proceso, no la antigüedad económica del dato. Un aggTrade con `event_time` de 24 horas atrás y `observed_at` actual produjo evidencia `QUALIFIED`, `data_age_ms=0` y cobertura completa en un probe local.

**[confirmed]** El bloqueo de capital real sigue presente, pero el override del endpoint no valida el hostname parseado. Cualquier URL HTTPS cuyo texto contenga un dominio permitido pasa el gate y recibe la API key y firma.

**[confirmed]** El dashboard cuenta cualquier `order_side` como orden y lo pinta como éxito aunque `order_status` sea parcial y la razón sea `ORDER_NOT_FILLED`. **[confirmed]** La suite existente cubre el dashboard legado y seguridad básica del adapter, no la máquina de estados V2.

<details><summary>Details</summary>

## El checkpoint no cierra la transacción de una orden

**[confirmed]** El runner persiste el estado de decisión antes de enviar la orden, pero sólo registra el fill en el engine después de que el adapter responde y escribe el journal al final (`realtime_demo.py:891-949`). Si Binance acepta un BUY y el proceso cae antes de `on_fill`, el restart encuentra un state file existente, omite `recover_engine_state`, reconcilia una posición LONG y adopta el ticker del restart como `entry_price`, no el fill real. Eso desplaza stop inicial, activación y trailing; debe persistirse un intent pendiente con client ID y resolverse contra Binance al arrancar, o implementarse una secuencia transaccional equivalente.

**[confirmed]** `EngineStateStore.load` propaga JSON truncado, esquema inválido o versión incompatible, y el fallback al journal sólo corre cuando `load()` devuelve `None` (`realtime_demo.py:490-526,835-851`). Corrupción de disco, edición operacional o una migración dejan el proceso sin recovery. El arranque debe distinguir checkpoint ausente, inválido e incompatible, conservar el fail-closed y ofrecer recuperación explícita desde journal+cuenta con auditoría.

## Los fills parciales existen aunque la decisión se cambie a HOLD

**[confirmed]** La condición de éxito exige `raw_status == "FILLED"`, cantidad positiva y precio positivo (`realtime_demo.py:928-943`). `PARTIALLY_FILLED` se convierte en `HOLD/ORDER_NOT_FILLED` sin llamar `on_fill`, aunque las cantidades ejecutadas representen una ejecución real. La reconciliación adopta una posición sólo si supera el umbral de dust y usa ticker como entry; un partial BUY menor al umbral sigue pareciendo FLAT y puede habilitar otra entrada. Debe modelarse como outcome ejecutado, actualizar estado por cantidad/precio llenados y decidir explícitamente cancelación, residual y reintento.

**[confirmed]** `_order_result` copia el side solicitado en vez de validar el side de la respuesta, y el runner no comprueba exchange order ID, client order ID esperado, quote ejecutado ni cambio reconciliado en la dirección esperada. Estas verificaciones deben ocurrir antes de considerar el fill definitivo.

## Un dato viejo se vuelve fresco al llegar tarde

**[confirmed]** `observe` guarda `event.observed_at` como reloj de precio y BBO, `snapshot` deriva `data_age_ms` de esos campos y `process_event` evalúa con el mismo `observed_at` (`realtime_demo.py:243-247,354-404,867-870`). El `event_time` de aggTrade sólo alimenta la ventana de flow; no invalida el precio usado por la decisión. Un probe con event time 86,400 segundos viejo produjo `qualified=True`, `reason=QUALIFIED` y edad 0. Se necesita un budget por event/exchange time, rechazo de regresiones y lateness, y una regla específica para BBO cuando Binance no provea reloj económico.

## El override DEMO no valida el host real

**[confirmed]** `DemoExecutionConfig.base_url` acepta el override si comienza con `https://` y contiene `demo-api.binance.com` o `testnet.binance.vision` (`binance_execution.py:57-65`). `https://demo-api.binance.com.evil.example` pasa esa validación; `_request` después envía `X-MBX-APIKEY` y la query firmada a ese host (`binance_execution.py:107-114`). Debe parsearse la URL, exigir hostname exactamente igual a uno permitido, rechazar userinfo/puerto/path inesperados y construir el origen desde valores canónicos.

## El dashboard convierte intentos incompletos en éxito

**[confirmed]** `build_floor` define success por la presencia de `order_side`, antes de considerar `ORDER_NOT_FILLED`, y `build_state` cuenta BUY/SELL con el mismo criterio (`dashboard.py:72-93,125-129,181-183`). Un registro `HOLD`, `ORDER_NOT_FILLED`, `PARTIALLY_FILLED`, `order_side=BUY` produjo execution `success`. Los contadores y estados deben distinguir intents, fills completos, fills parciales y rechazos usando `order_status` y cantidades ejecutadas.

**[confirmed]** `build_state` lee y recorre el journal completo en cada polling de cinco segundos para equity y contadores. El costo crece linealmente durante toda la vida del proceso; debe mantener snapshots incrementales o limitar/compactar la serie servida antes de operación prolongada.

## Los gates V2 no tienen pruebas ejecutables

**[confirmed]** Ningún test importa `application.realtime_demo` ni `adapters.binance_stream`; `test_live_demo.py` cubre V1 y `test_execution_adapter.py` no cubre SELL base, parseo de respuestas, idempotencia ni partial fills. Las 79 pruebas y 164 subtests pasan, al igual que Ruff y mypy sobre los archivos revisados, pero no ejercitan structural/tactical, SELL persistence, state recovery, trailing activation o freshness. Deben añadirse escenarios deterministas de restart en cada ventana de crash, fills parciales, eventos late/out-of-order y transición exacta del trailing antes de deploy.
